Command-Line Options Reference

Use this reference to look up builder and preview options. Generic names such as My Application stand for your own project; Invoice Viewer continues the worked configuration example from Section 4: Configuration Options. The installed tool’s --help output is the definitive reference for its version.

The overview highlights common builder options; the detailed entries that follow cover the complete command-line reference. For worked examples, see Section 4: Configuration Options.

Command-Line Practical Reference

The detailed reference below explains each option’s syntax, purpose, default behaviour, and recommended use.

Reading the Reference

Each entry uses the same fields: option name, importance, purpose, repeatability, where to use, syntax, when to use, behaviour if omitted, example, and important note.

Option name, aliases, and short or long forms

Importance

A brief description of what the option does

Repeatability

Where to Use

Syntax

The option followed by its value, if required. Angle brackets mark a value to supply; square brackets mark an optional value.

When to use

A description of when to use this option

If omitted

What happens when the option is absent from both the command line and the loaded options files, including any default or build requirement.

Example

An example of the option and any parameter values

Important note

Constraints, interactions, or cautions to consider when using the option.

Understanding Importance

Importance describes the option’s role in a normal application build:

  • Required - a normal build needs this information. Input may be supplied by --input or the positional [JAR|DIR] form; information and scaffolding commands do not require application input.
  • Recommended - set this deliberately for a distributed application, even though Snug can build without it.
  • Optional - use this when the application or workflow needs it. Optional settings can still affect build success or runtime behaviour.

Understanding Repeatability

Repeatability describes how many values an option is intended to receive. It does not mean that duplicate single-value options are always rejected.

  • Single - supply one effective value or flag. Avoid duplicate occurrences.
  • Multiple - repeat the option to supply additional values. Builder --jvm-arg and --localisation values accumulate across loaded options files and the command line.

Understanding Where to Use

Where to Use distinguishes saved build settings from commands best entered directly:

  • Options - reserved for settings that belong only in snug.options. No entry in this reference currently uses this classification.
  • CLI only - recommended placement for tooling, scaffolding, information, and diagnostics. This is a usage recommendation, not a blanket parser restriction: some diagnostic flags also work in options files, while file-selection and init flags receive special handling. Snug Preview reads its flags directly from the command line.
  • Both - use the setting in a loaded options file or on the builder’s command line. Command-line single-value settings take precedence; repeatable --jvm-arg and --localisation values accumulate.

Snug Builder (snug.exe) Options Reference

--input

Required input

Selects the JAR file or directory of JAR files that Snug should package.

Single

Both

Syntax

--input <JAR|DIR>

When to use

Use it when you want the input source to be explicit, especially in snug.options.

If omitted

Packaging fails if neither --input nor positional input supplies a JAR file or directory.

Example

--input build\libs\my-app.jar

Important note

The positional [JAR|DIR] form is also accepted in an options file. For clarity, this book recommends using --input in snug.options.

--name

Recommended

Sets the application's display name, used in Windows metadata and Snug's local application identity.

Single

Both

Syntax

--name <NAME>

When to use

Always set this to the real application name for a normal build.

If omitted

Snug uses the input JAR filename without its .jar extension, or the input directory name.

Example

--name "My Application Name"

Important note

Together with --company, this value identifies the application in Windows metadata and Snug’s application cache.

--company

Recommended

Sets the company or vendor name for Windows application identity.

Single

Both

Syntax

--company <COMPANY>

When to use

Always set this to the real company or vendor name for a normal build.

If omitted

Snug uses the resolved application name.

Example

--company "My Company"

Important note

Together with --name, this value identifies the application in Windows metadata and Snug’s application cache.

-o, --output

Recommended

Sets the path and filename of the Windows executable that Snug creates.

Single

Both

Syntax

--output <EXE>

When to use

Use it when you want to control the output filename or location.

If omitted

Snug chooses the default output name for the build which is based on the input JAR file(s) or directory name.

Example

--output dist\invoice-viewer.exe

Important note

If the destination executable already exists, Snug overwrites it.

Example

--version 1.2.0

The version may contain one to four numeric components, each from 0 to 65535.

--update-url

Optional

Adds a "Check for a newer version" button to launcher error dialogs.

Single

Both

Syntax

--update-url <URL>

When to use

Use it when users should have an easy path to a download or update page.

If omitted

Launcher error dialogs do not include an update button.

Example

--update-url https://example.com/downloads

Important note

Use a stable HTTPS page where users can find an updated version of your application. The button opens the URL in the user's default browser. Snug does not check whether the page exists or provides a download, and it does not automatically check for, download, or install application updates.

--manifest

Optional

Embeds a Windows application manifest as RT_MANIFEST.

Single

Both

Syntax

--manifest <XML>

When to use

Use it only when the application needs a custom Windows manifest.

If omitted

No custom manifest file is embedded.

Example

--manifest snug\app.manifest

Important note

Snug checks that the supplied manifest is well-formed XML and rejects malformed XML during the build. This check does not confirm that the manifest contains valid or appropriate Windows application settings.

You remain responsible for the manifest's contents. Test the finished executable on the Windows systems you intend to support.

--main-class

Optional

Overrides the Main-Class that Snug would otherwise use in the manifest.

Single

Both

Syntax

--main-class <CLASS>

When to use

Use it when discovery is ambiguous or you intentionally want a different entry point.

If omitted

Snug reads Main-Class from the input JAR, or from the first JAR in filename order for a directory. It does not fall back to a later manifest.

Example

--main-class com.example.Launcher

Important note

The class must be a valid application entry point available in the packaged JARs.

At packaging time, use --find-main with the input JAR or directory to inspect candidate entry points.

--find-main

Optional

Single

CLI only

Syntax

--find-main

When to use

Use it when you need to inspect or troubleshoot application entry points.

If omitted

Snug proceeds with its normal main-class handling.

Example

--find-main

Important note

This is a diagnostic command and does not replace --main-class when you intentionally need an override. It does not create a build log.

Single

Both

--jvm-arg

Optional

Passes an option directly to the JVM when Snug creates it.

Multiple

Both

Syntax

--jvm-arg <OPTION>

When to use

Use it only when the Java application requires a specific JVM option, such as a memory limit or system property.

If omitted

The JVM starts without any additional options supplied by Snug.

Example

--jvm-arg=-Xmx2g

Important note

Invalid or unsupported JVM arguments can prevent the Java runtime from starting.

--download-jdk

Optional

Controls Snug's managed Java-runtime download behaviour.

Single

Both

Syntax

--download-jdk <off|auto|force>

When to use

Use it to control runtime downloads. Normally keep auto. Use force to exercise the managed-runtime path; a compatible Snug-managed cached runtime may still be reused.

If omitted

Snug uses automatic runtime discovery and download behaviour - i.e. the value is set to auto.

Example

--download-jdk=force

Important note

Using off can leave the application unable to start on a machine without a compatible Java runtime.

--cache-dir

Optional

Overrides the application's default per-user cache location.

Single

Both

Syntax

--cache-dir <ABSOLUTE_DIR>

When to use

Only when a deployment has a compelling storage requirement.

If omitted

On Windows, Snug normally stores application JARs under %LOCALAPPDATA%\snug\<company>\<app>\.

Example

--cache-dir "D:\ApplicationCache"

Important note

Use an absolute path. The directory need not exist at build time, but it must be usable on the target computer. This setting changes the application-JAR cache, not the separate managed-JDK cache. An explicit --cache-dir disables the shared JAR store, even if the selected folder is on the same drive.

--splash-max

Optional

Sets the recommended maximum splash dimensions used for a build-time warning.

Single

Both

Syntax

--splash-max <WxH|off>

--allow-multiple-instances

Optional

Allows more than one copy of the application to run at the same time.

Single

Both

Syntax

--allow-multiple-instances

When to use

Use it only when separate simultaneous copies of the application are genuinely useful.

If omitted

If the application is already running, Snug attempts to activate the existing instance instead of starting another copy.

Example

--allow-multiple-instances

Important note

The single-instance default is best-effort, not an exclusivity guarantee. Window activation may fail, and an unavailable instance lock allows another instance to start. Arguments from a second launch are not delivered to the running instance.

Diagnostic Messages Reference

The codes

SNUG-CFG-001 - Arguments or options could not be parsed

Cause. Snug rejected the command line or an options file. The message is from the in-build command line parser, unchanged.

Remedy. Fix the argument that the message names. The build log also records the failure.

Covers. Only the syntax. A file that parses but says something nonsensical is a different code.

SNUG-CFG-002 - The effective configuration is invalid

Cause. The options were syntactically fine but do not describe a build that Snug can perform - no input at all, or an output on a platform whose embedded launcher is not a Windows Portable Executable.

Remedy. The message names the option to change.

Input

SNUG-INPUT-001 - The input is missing or unusable

Cause. The JAR or directory named by --input (or the positional argument) does not exist, cannot be read, or is not a JAR.

Remedy. Check the path. The message shows the path snug tried.

SNUG-INPUT-002 - A directory entry could not be read

Cause. A directory listed as the input contained an entry that could not be read - it could not be opened, or it was empty - so it was left out of the build.

Why it is a warning and not an error. The build carries on with the JARs it could read. This used to be a silent skip - a failed read was discarded and the build carried on with fewer JARs than the directory held, with nothing on screen to say so. It used to be worse than silent: the read failure aborted the whole build as SNUG-INTERNAL-001, which tells the user to report a snug bug they did not cause.

Covers. The entry is named, and the build says what it did about it. A directory in which every JAR was skipped is a different problem - there is nothing left to build - and is reported as SNUG-INPUT-001.

Remedy. Check the directory's permissions if a JAR you expected is missing from the build.

Archives

SNUG-JAR-001 - The supplied archive is not a readable ZIP

Cause. A file that was handed to snug as a JAR could not be opened as a ZIP archive.

Remedy. Re-export the JAR, or remove it from the input.

Covers. Every supplied archive is opened, including when --main-class overrides the manifest. An override must not turn an archive that cannot be read into one that is silently embedded: the build would succeed and the application would fail at runtime.

SNUG-MANIFEST-001 - The manifest could not be read

Cause. A JAR's META-INF/MANIFEST.MF could not be read: the entry is there, but reading it failed - a corrupted archive, most often.

Remedy. Re-export the JAR, or pass --main-class <CLASS> to name the entry point directly. The manifest is only read when snug has to find the entry point itself.

Covers. A JAR that is not a readable ZIP is reported as SNUG-JAR-001 instead, and the manifest check is skipped rather than reported twice. This is the user's archive, not a snug bug, so it never arrives as SNUG-INTERNAL-001.

Entry point

SNUG-MAIN-001 - No usable entry point was selected

Cause. No JAR declares a Main-Class and --main-class was not given. The launcher would have nothing to call - neither a main method nor the JavaFX Application.launch fallback can be reached without a class name.

Remedy. Pass --main-class <CLASS>, or run snug --find-main to list the classes that declare one.

This is a behaviour change. Snug used to build an executable with no entry point and let it fail on the user's machine.

SNUG-MAIN-002 - The selected class is not in any supplied JAR

Cause. --main-class names a class that no supplied JAR contains.

Remedy. Check the spelling, and check that the JAR containing it was included in the input.

Covers. The classpath that is being embedded — the JARs snug was given. A class that arrives some other way (a Class-Path manifest reference, a nested JAR) is not on that classpath and is reported as absent.

SNUG-MAIN-003 - The entry-point method could not be verified

Cause. Snug could not confirm that the selected class — or one of its ancestors — declares public static void main(String[]). The class file may not have been readable, or the chain may have left the supplied JARs.

Why it is a warning. The Windows launcher supports the JavaFX Application.launch fallback, and a main method can be inherited. A blanket requirement for a declared method would reject working applications.

Covers. The ancestors are walked, so an inherited main is confirmed rather than reported. A class that extends javafx.application.Application is left alone too: the launcher starts it through Application.launch rather than through main.

SNUG-MAIN-004 - Several JARs declare different entry points

Cause. More than one supplied JAR declares a Main-Class, and they disagree. Snug reads the first JAR by filename; that is an ordering accident, not a decision anybody made.

Remedy. Pass --main-class <CLASS> to choose explicitly.

SNUG-MAIN-005 - The same entry class appears in more than one JAR

Cause. Two JARs contain the same class. The first JAR by filename wins.

Remedy. Remove the duplicate, or pass --main-class if the other copy is the one you want.

Dependencies

SNUG-DEP-001 — A manifest names an external classpath entry

Cause. A JAR's manifest declares a Class-Path referring to something outside the archive.

Remedy. Snug does not resolve, download or bundle manifest Class-Path entries - that is what a dependency resolver is for. Build the application as a fat JAR instead.

SNUG-DEP-002 — A nested JAR was found and not resolved

Cause. The archive contains a JAR inside a JAR.

Remedy. Snug does not resolve nested JARs. Unpack them first, or use a fat JAR that has them flattened.

Covers. One note per supplied JAR that holds them, so a Spring Boot fat JAR does not produce a line per dependency.

Bytecode

SNUG-JAVA-001 - Bytecode needs a newer Java than --min-java

Cause. A class in the supplied JARs was compiled for a newer Java release than --min-java allows. Class-file major 69 is Java 25; the release is major - 44.

Severity. An error for the selected entry class — the build would produce an executable that cannot start. A warning for every other class: optional code may never load, and a fat JAR routinely carries classes for newer releases than the one it runs on.

Remedy. Build with --min-java set to the release the entry class needs, or supply a JAR compiled for the older release.

Multi-release. An archive that declares itself multi-release serves the highest overlay at or below the configured release, falling back to the root copy. An overlay for a newer Java never raises the minimum.

Covers. Every class in every supplied JAR. The version lives in the first eight bytes of a class file, so the check reads eight bytes per class and covers the whole archive — with no scan-window caveat. This is a different guarantee from SNUG-MAIN-003, whose method-table check is bounded by a 64 KB prefix read; the two are reported separately because they are not equally strong.

Does not cover. Bytecode compatibility is not API compatibility. A class compiled for Java 25 can still call a method that does not exist in the Java 17 runtime you point --min-java at. Snug checks the class version, not the API surface.

SNUG-JAVA-002 - Preview bytecode

Cause. A class was compiled with preview features enabled, which marks it with minor version 0xFFFF.

Remedy. Pass --jvm-arg=--enable-preview to run preview classes. Snug does not add it for you - a preview class is not runnable without it, and silently enabling preview mode would change the behaviour of every other class in the application too.

Resources

SNUG-RESOURCE-001 - A supplied resource is invalid

Cause. An icon, splash image, Windows manifest or localisation bundle could not be prepared: the file could not be read, the image would not decode, the manifest is not well-formed XML, or a localisation directory holds a file that does not follow the naming convention.

Remedy. The message names the file.

Covers. The Windows manifest check is XML well-formedness only. It is not a schema check, and it does not validate the manifest against what the launcher actually activates.

Does not cover. An icon that cannot be read is reported as SNUG-OUTPUT-002 in a real build, because the icon is read while the executable is being stamped rather than while the payload is being assembled. A --dry-run reports it as SNUG-RESOURCE-001, because a dry run does the same checks without the write.

SNUG-RESOURCE-002 - The splash image is larger than recommended

Cause. The splash PNG is larger than the launcher's preferred size, so it will be scaled at runtime.

Remedy. Shrink the image. The build proceeds.

Localisation

SNUG-LOCALISATION-001 - A localisation bundle is incomplete, or has drifted

Cause. A supplied translation bundle does not cover every key in the built-in English baseline, or it uses different placeholders than the baseline does.

Why it is a warning and not an error. A missing key falls back to the built-in English text, so the launcher still runs and the build is not worth refusing. A drifted placeholder is reported rather than repaired.

Remedy. Copy the missing keys across from the baseline, and run snug --list-tokens for the placeholder contract.

Output and log

SNUG-OUTPUT-001 - The output and an input are the same file

Cause. The output path names one of the build's inputs: a JAR, the options file, a localisation file, the build log, or a JAR inside a directory input.

Remedy. Pass a different output path. Snug reads every input into memory before writing anything, so proceeding would destroy the input with no backup.

SNUG-OUTPUT-002 - The output could not be written

Cause. The executable could not be created — the path is not writable, or the icon, version resource or manifest could not be stamped into it.

Remedy. The message carries the underlying cause.

SNUG-LOG-001 - A write to the log failed

Cause. The log could not be written completely, usually because the disk filled or the file was locked.

Remedy. The build's own result is unaffected — snug reports this rather than claiming a complete log was saved.

SNUG-LOG-002 - The log destination could not be opened

Cause. The requested --build-log path could not be opened for writing, or it names one of the build's own input files. A path whose parent directory does not exist is the common case: snug does not create directories, so the open fails with the operating system's own "path not found" rather than making the directory first.

Remedy. Point --build-log somewhere writable, and make sure the parent directory exists. Snug stops before creating the executable: a build whose report nobody can read is not a build worth shipping. The reason is written to a temporary log when one can be made.

Internal

SNUG-INTERNAL-001 - Something unexpected went wrong

Cause. A failure snug did not anticipate. The message carries the underlying error.

Remedy. This is a bug. Please report it with the build log.

Covers. Only failures that arrive without a code of their own. A problem the user can act on - a path that does not exist, a file that cannot be read, a bundle that does not parse - carries that problem's own code instead, because telling someone to report a bug they cannot cause is worse than useless.
