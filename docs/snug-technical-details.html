Chapter 13

Snug Technical Details

This section looks underneath the polished Windows executable and explains what Snug is doing behind the scenes.

You do not need to understand this section to use Snug successfully; the earlier sections are enough to build and configure an application. This section is for readers curious about what happens when Snug builds and launches an application.

What Snug Actually Builds

When you run snug.exe, Snug does not convert your Java application into native Windows machine code. Your application remains a Java application; instead, Snug creates a native Windows executable that contains the Snug launcher together with the Java application and the information needed to launch it.

At a high level, the result looks like this:

Windows executable

↓

Native Snug launcher

↓

Embedded application files and configuration

↓

Your Java application

Image: Technical overview diagram showing a Snug-built .exe containing the native launcher, Windows resources, configuration and embedded JAR payload.

The advantage of this design is that the person receiving the application sees a normal Windows executable, while the Java application itself can remain packaged in the familiar JAR format.

The Builder and the Launcher

There are two distinct pieces of Snug involved in this process.

The Builder

snug.exe is the builder, and its job is to take your JAR file or files, your Snug configuration, and any additional resources such as an icon, splash screen, or manifest, and produce the finished Windows executable.

Once the executable has been built, the person receiving your application does not need snug.exe.

The Launcher

The Snug launcher is the native Windows program that becomes part of the executable created by the builder. Its job begins when the user double-clicks the finished .exe, at which point it reads the embedded configuration, prepares the packaged application, locates or obtains a suitable Java runtime, and starts the Java application.

This separation is important:

snug.exe builds the application and inserte.

The embedded Snug launcher runs the application.

Anatomy of the Windows Executable

A Snug-built application is a normal Windows Portable Executable, usually referred to simply as a PE executable.

Windows executables contain a number of sections and resources. The exact layout is an implementation detail, but the broad structure is useful to understand.

A Snug executable contains:

  • the native launcher code
  • Windows executable metadata
  • the application icon
  • an optional Windows manifest
  • an optional Snug splash image
  • Snug configuration
  • the packaged Java application files

The Java application data is stored inside the executable as Windows resources rather than as loose files alongside the .exe.

The Quick-Start output gives a hint that this is happening when Snug reports that the application payload has been written as RT_RCDATA.

Technical: RT_RCDATA is a Windows resource type used for application-defined binary data. Snug can use this resource area to carry packaged application data inside the executable.

[IMAGE PLACEHOLDER: Simplified PE executable diagram showing .text/.data/.rsrc, with the launcher in executable code and the JAR/configuration/icon/splash represented inside resources.]

Windows Resources

Several of the options described earlier in this book become Windows resources in the finished executable.

For example:

  • the application icon becomes an executable icon resource
  • version, company, and description information become Windows version metadata
  • a custom manifest becomes an RT_MANIFEST resource
  • packaged application data is carried as application-defined resource data
  • the Snug splash image is available to the native launcher before Java starts

This is why Windows can display information about the executable before the Java application has run at all.

The Java Application Remains a JAR

Snug does not rewrite your Java bytecode into a different programming language; the JAR you provide remains the application that is eventually started by Java.

Snug's job is to package that application, carry it inside the Windows executable, prepare it when required, and provide the native launch experience around it.

This also means that normal Java concepts still matter. Your JAR still needs to be a valid runnable Java application, and the runtime used by Snug must be suitable for that application.

What Happens When the Executable Starts

When a user double-clicks a Snug application, Windows starts the native Snug launcher, which performs a sequence of preparation steps before handing control to the Java application.

The exact details may evolve between Snug versions, but the current design can be thought of as:

  1. Read the embedded Snug configuration.
  2. Identify the packaged application.
  3. Prepare or reuse the cached application files.
  4. Determine whether a suitable Java runtime is available.
  5. Obtain runtime components if the configuration allows it and they are required.
  6. Start the Java runtime.
  7. Launch the configured Java application.
  8. Leave the Java application running normally.

Application Identity and the Cache

The --name and --company values are more than cosmetic labels.

They are used by the launcher as part of the identity of the application on the user's computer.

In the current Windows implementation, Snug stores prepared application data beneath the user's local application-data area. A typical path follows this general pattern:

%LOCALAPPDATA%\snug\<Company>\<Application>\...

Within that application area, Snug can keep prepared application files associated with the packaged JAR.

The current launcher also uses a SHA-256 hash of the primary JAR as part of identifying a particular packaged application payload. This allows different builds of an application to be kept distinct when the application content changes.

For example, a diagnostic log may contain entries such as:

app: Synapticloop / Snug JavaFX Demo
primary JAR sha256: <hash>
cached jars: 1

Cache lifecycle and cleanup

Snug retains recently used application payloads so that switching between builds need not always require another extraction. It periodically reviews the application cache and removes older or unused entries, taking account of recent use and storage consumption. The currently running build is protected from eviction. This is automatic; the user normally does not need to delete cached files manually.

Downloaded Java runtimes are managed separately from extracted application files. Cache cleanup should not be confused with a runtime upgrade: Snug does not automatically replace an existing downloaded JDK with every newer security release.

The exact directory names, retention thresholds, and cleanup intervals are implementation details and may change in later versions of Snug.

IMPORTANT: This is why --name and --company must uniquely identify your application. Reusing the same identity for unrelated applications risks making their local application data collide.

Where Snug Stores Its Files

Snug keeps the files it needs to launch applications inside the current user's Windows Local AppData directory.

The base directory is:

%LOCALAPPDATA%\snug

%LOCALAPPDATA% is a Windows environment variable that points to the local application-data directory for the currently signed-in user. On a typical Windows installation, the Snug directory will therefore resolve to a location similar to:

C:\Users\YourName\AppData\Local\snug

Downloaded Java runtime components are stored in:

This runtime is stored separately from individual applications so that Snug can reuse it for future application launches rather than downloading another copy for every application.

Files belonging to an individual application are stored beneath the company and application names supplied when the executable was built. For example:

%LOCALAPPDATA%\snug\SynapticLoop\Snug JavaFX Demo

Within an application's directory, Snug keeps the prepared JAR files, launcher logs, and other cached files it needs to start and diagnose the application.

In normal use, you should not need to modify anything inside these directories manually. Knowing where they are stored is useful, however, when troubleshooting an application, examining its launcher logs, or understanding which files Snug has cached.

Why Use a Cache?

The executable contains the packaged application, but Java works most naturally with files that are available through the filesystem, so preparing those files once and reusing them on later launches avoids unnecessary work.

The cache also gives Snug a stable place for launch-related files and diagnostics without requiring the application to write into the directory where the .exe happens to be stored.

This matters because the executable may have been copied to a desktop, downloaded into a temporary directory, placed on a network share, or stored somewhere the user should not modify directly.

Finding a Java Runtime

A Java application cannot run without a compatible Java runtime, so the launcher needs to determine whether an appropriate runtime is already available or whether runtime components need to be obtained.

The required Java version is part of the packaged launch configuration, and at startup Snug can inspect the available runtime situation and apply the runtime-download behaviour configured when the executable was built.

The user-facing result was described in Section 3. Technically, the important point is that runtime selection happens in the native launcher before the Java application itself is started.

Downloaded Runtime Components

Snug deliberately does not have to place a complete Java runtime inside every application executable. When runtime download is enabled, required runtime components can instead be obtained when necessary and reused for future launches, keeping the packaged application separate from the runtime environment that executes it.

For organisations distributing several Java applications, this can also avoid every executable carrying its own full copy of Java.

The exact download source, runtime selection rules, and cache layout are implementation details and should be checked against the version of Snug being used.

At the time of writing, Snug's managed runtime download uses Eclipse Temurin.

The default minimum Java major version is 25, unless --min-java is configured differently.

Runtime and Cache Lifecycle

On the first launch, Snug identifies the application from its company and application name, then identifies the packaged application payload from the SHA-256 hash of the primary JAR. This determines the application cache area that belongs to the current build.

The launcher then looks for a compatible Java runtime according to the configuration stored in the executable. If an acceptable runtime is already available, it can be used immediately. If one is required and runtime downloading is enabled, Snug can obtain its managed runtime, verify the download, extract it, and keep it in the Snug runtime cache.

Later launches reuse the cached application files and managed runtime where they are still suitable. Snug does not need to download Java every time the application starts, and a newer Temurin release appearing upstream does not by itself replace the runtime that has already been cached.

When the packaged JAR changes, its hash changes as well. Snug prepares the application cache for the new payload and can remove cached application files that belong to the previous hash. The Java runtime cache is separate from this application-payload cache, so changing the JAR does not normally require the runtime to be downloaded again.

If a newer managed runtime is deliberately obtained, Snug keeps runtime versions separate while an older version may still be in use. Running applications continue with the runtime they started with, and an older managed runtime can be retired once Snug has confirmed that no running application still depends on it.

Runtime Versions and Running Processes

Snug keeps downloaded runtime versions separate rather than replacing the files of a runtime that may already be in use. If a newer compatible runtime is obtained, new application launches can use the newer version while applications that are already running continue using the version with which they were started.

Before an older runtime is removed, Snug needs to know whether any running Snug application is still using it. When Snug launches Java, it records the process and the runtime associated with that process.

A saved process identifier is treated as a pointer to a possible running process rather than proof that the process is still the original application. Process identifiers can eventually be reused by Windows, so Snug validates the process before treating the runtime as active.

If the recorded process is no longer valid, the stale process record can be removed. If the process is still running and is using that runtime, the runtime remains in place.

This allows Snug to update managed runtime components without interrupting running applications. The old runtime is retired only after it is no longer being used.

Starting Java

Once the application files and a suitable runtime are available, the launcher starts Java and hands control to the packaged application. From that point onward, it behaves as a Java application.

For a JavaFX application, JavaFX initialises and the application's normal windows, stages, and controls are created by the Java application itself.

This is also the point at which an application-managed Java or JavaFX splash screen may appear if the application has been configured to use one.

The Snug splash and a Java application splash therefore belong to different layers:

Snug splash

Native launcher

Java/JavaFX splash

Java application startup

That distinction is why the Snug splash can appear before Java itself has finished starting.

When the Java Application Exits

Once Java is running, most shutdown behaviour belongs to the Java application rather than to Snug. Closing the application's windows and allowing the application to finish normally is an ordinary shutdown.

If the JVM or application terminates unexpectedly, Snug can tell that the native application process has ended, but an exit status alone cannot always explain why it ended. A non-zero exit code, an abrupt termination, a JVM failure, and a failure in a native library can all indicate that something went wrong, but they are not the same failure.

An out-of-memory condition is also not automatically equivalent to an application crash. Java may throw an OutOfMemoryError that the application handles, or the application may become unable to continue and terminate. JVM options can also change what happens after an out-of-memory condition. Snug should therefore treat the resulting process termination as evidence of an abnormal end rather than attempt to diagnose the exact Java exception from the exit code alone.

If an application ends unexpectedly, the Snug launcher log is a useful first place to look because it describes the launch environment and the runtime that was selected. Application logs, Java exception output, or JVM crash files may then provide the reason for the failure. Snug can report that the application ended abnormally, but detailed diagnosis remains the responsibility of the Java application and JVM diagnostics.

Application Arguments

The launcher can pass configured command-line arguments through to the Java application, allowing a packaged application to receive the same type of startup arguments it could receive when launched directly with Java. Whether an individual application makes use of those arguments is entirely up to that application.

Technical: Arguments intended for the Java application should be distinguished from Snug builder options. Builder options control how the .exe is created; forwarded application arguments affect the Java application when the finished .exe is run.

The Windows Manifest

A Windows manifest is metadata that tells Windows about particular behaviours expected by an executable, such as DPI awareness or the requested execution level. When --manifest is supplied, Snug embeds it into the finished executable at build time, allowing Windows to inspect and use the manifest before the Java application starts.

If you do not have a specific Windows requirement that needs a custom manifest, there is normally no reason to create one.

IMPORTANT: Snug will simply include the manifest file. It does not inspect, parse, or validate the manifest in any way. If there is an error in the manifest, Snug will still include it and you may not find the error until someone launches the application and the behaviour is not as expected.

Logging and Diagnostics

The Snug launcher writes diagnostic information that can be useful when an application does not start as expected.

A launcher log can include information such as:

  • the application and company identity
  • the application version
  • the cache location
  • the SHA-256 hash of the primary JAR
  • the number of cached JARs
  • the required Java version
  • runtime-download behaviour
  • whether arguments are forwarded
  • the Java main class
  • errors encountered during preparation or launch

Troubleshooting a Launch

If a Snug application builds successfully but does not launch correctly, a useful technical troubleshooting sequence is:

  1. Confirm that the same JAR runs correctly outside Snug.
  2. Confirm that the Snug application was built with the intended configuration.
  3. Check the launcher log.
  4. Look for the detected Java requirement and runtime information.
  5. Check whether the packaged application files were prepared successfully.
  6. Check the reported main class and application arguments.
  7. Rebuild with the current version of Snug if the executable was produced by an older release.

The aim is to separate a Java application problem from a packaging or launcher problem. If the JAR itself does not run correctly, packaging it with Snug will not repair the Java application; if the JAR runs normally but the Snug executable does not, the launcher log is the best place to start.

Code Signing Is Separate from Packaging

Creating a Windows executable and digitally signing one are two different operations. Snug can create the executable and add metadata such as the company name, description, icon, and version, but that metadata does not constitute a digital signature.

A code-signing certificate is used to cryptographically identify a publisher and allow Windows to verify that a signed executable has not been altered since it was signed.

The --company option therefore should not be confused with code signing. Setting:

--company "My Company"

adds application identity used by Snug and Windows metadata, but it does not cause Windows to treat the executable as digitally signed by My Company.

If code signing is required by your organisation or distribution process, it is a separate step performed after the Snug executable has been created.

Why Snug Does Not Bundle Everything

It would be possible to build a Java desktop package that contains an entire Java runtime inside every application, but Snug deliberately takes a different approach. The application executable contains the launcher and application payload, while a suitable runtime can be located or obtained separately. There are trade-offs to both approaches.

Bundling a runtime can make an application more self-contained, but it can also make every application considerably larger. Reusing runtime components keeps the individual application artefact smaller and avoids duplicating the same runtime across multiple applications.

Snug's design is therefore focused on providing a small, familiar Windows entry point while managing the Java requirements behind it.

Keeping the Layers Separate

The easiest way to understand Snug technically is to think in layers:

Windows

Starts the native executable and reads its Windows resources.

Snug launcher

Prepares the packaged application, manages the runtime requirement, and starts Java.

Java runtime

Provides the environment needed to execute the Java application.

Java application

Contains the behaviour and user interface that you actually built.

Each layer has a different responsibility, and this separation is one of the reasons Snug can remain largely invisible to the person using the application.

Technical Details Will Evolve

The user-facing concepts in this book are intended to remain stable, but implementation details such as cache locations, internal resource identifiers, runtime-selection logic, and launcher internals may evolve between releases.

When diagnosing a particular build, the most useful sources of truth are therefore:

  • the --help output from the Snug version being used
  • the launcher log produced by that application
  • the release notes and documentation for that version

The earlier sections of this book concentrate on the stable experience: build the application, configure how it should behave, and give the user a Windows executable.

This section explains the machinery that makes that experience possible.
